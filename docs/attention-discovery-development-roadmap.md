# Urus 变化发现改造：详细开发路线图

日期：2026-09-20。本文把《变化发现与分析页面改造方案》拆成可逐步验收的开发工作。系统仅供个人使用，优先复用现有 Observation Run、CrossSectionProjection、Strategy Decision 与 Group Snapshot；每一步都必须能独立运行，不引入通用规则平台、消息队列、事件总线或多用户权限体系。

当前进度：第 0–5 步已完成实现并经主 Agent 复核；第 6 步的首个双快照板块阶段切片也已通过自动化与真实浏览器验收。当前本地真实数据中，同一 theme group version 只有同日快照，尚不具备连续多日、同口径的板块历史，因此“持续天数”“最近加速”和第 7 步的持续跷跷板结论仍关闭。该限制来自证据条件，不用单日涨跌幅或同日重跑结果替代。

## 1. 本轮目标与范围控制

本轮先完成一个可用闭环：打开网站先看到“什么发生了值得重新看”，再带着同一份证据进入个股页或指标／策略一览页。首页只陈述已有冻结数据能证明的变化，不在第一轮声称已经识别出可靠的板块跷跷板。

第一轮明确不做：全市场扫描、自动交易、推送通知、AI 自动解释、复杂个性化、已读／忽略生命周期、任意板块两两计算、把多个异构策略合成为胜率、为了未来扩展建立抽象规则 DSL。

三个模块边界：

- **变化发现投影（Discovery Projection）**：读取一份 Observation Run 及其前一可比证据，输出已去重、可解释、可跳转的变化记录。它是只读投影，不采集数据，不修改策略结果。
- **个人重点关注（Focus List）**：只记录用户重点关注的 symbol。它不改变 Universe、观察组或采集资格。个人使用场景下不增加账号和权限模型。
- **分析页面（Analysis Surfaces）**：首页、个股页、指标页和策略页只展示投影、排序与筛选；前端不重新计算市场事实。

删除检验：如果去掉变化发现投影，首页、个股页和横截面页会重新各自解释“什么变了”，去重、证据身份和跳转上下文会分裂。因此它应当是独立模块。Focus List 只有一个简单职责，不继续抽象成偏好平台。

## 2. 稳定接口

### 2.1 Discovery Projection

新增读取接口：

`GET /api/observation/runs/{run_id}/discovery`

目标响应最终包含三类记录：

1. `strategy_transition`：策略阶段、方向或可评估状态发生变化；
2. `indicator_transition`：指标跨越现有定义中的状态边界；
3. `group_phase_change`：已有 Group Decision Phase 的 state 或 impulse 发生变化，且样本支持允许展示。

第一个纵向切片先开放 `indicator_transition`；第 6 步已经增加基于当前与前一冻结 Group Snapshot 的 `group_phase_change`。`strategy_transition` 仍为 `deferred`。不得用当前值猜前值来凑齐缺失记录。

每条记录至少包含：

- 稳定 `event_id`，由 run、对比 run、类型、对象和 lens 身份确定；
- `kind`、symbol／group、全部 group 标签；
- 当前和对比交易日、run id、dataset／snapshot 证据引用；
- `before`、`after`、最多三条已有支持事实、已有反对／未满足条件；
- 可读的 `priority_reason`，以及确定性的排序元组；
- 指向个股或横截面页的目标路由参数。

同一 symbol、同一 lens、同一次变化即使出现在多个重叠观察组中也只返回一条记录，`group_ids` 和 `group_names` 合并。若不同观察组使用不同基准或证据身份，不能把数值强行合并；保留为不同上下文并标注原因。

第一轮不落库保存发现事件。它按现有冻结数据确定性生成；同一请求必须得到相同内容摘要。等真实使用证明需要跨日生命周期后，再增加持久化事件历史。

### 2.2 Focus List

新增最小写入接口：

- `GET /api/focus-symbols`
- `PUT /api/focus-symbols/{symbol}`
- `DELETE /api/focus-symbols/{symbol}`

只保存规范化 symbol 和创建时间。单机个人系统只需一张表，不添加用户表、标签、排序文件夹或同步协议。删除 Focus List 数据不会损坏任何市场证据。

### 2.3 跳转上下文

首页跳转携带 `runId`、`compareRunId`、`kind`、`lensId`、`symbol`／`groupId` 和 `eventId`。详情页先展示发现发生时的冻结证据；若已有更新数据，另给“查看最新”入口，不能静默替换。

## 3. 分步开发与验收

### 第 0 步：冻结基线和测试夹具

负责人：开发 Agent 执行，主 Agent 验收。

1. 运行当前后端 observation／cross-section 相关测试与前端关键测试，记录基线。
2. 选用已有测试工厂构造：两个可比 run、两个重叠观察组、一个重复 symbol、一条策略变化和一条指标变化。
3. 不复制整套生产 payload；夹具只覆盖接口需要的字段。

完成标准：现有测试结果已记录，新夹具能证明重复来源确实存在。

### 第 1 步：只读 Discovery Projection 的指标纵向切片

负责人：开发 Agent 实现和自动化测试；主 Agent 评审完整性。

1. 在 decision harness 中新增薄的 discovery 投影，只通过现有 `CrossSectionService` 聚合明确的指标状态变化，不重算指标。
2. 普通指标只合并事实签名一致的行；相对强弱还必须包含 benchmark 身份，不能只按 symbol+lens 合并。重复来源合并后保留全部组、snapshot 和 dataset 身份。
3. 在 observation API 注册读取端点。错误状态沿用现有 AppError 与质量表达。
4. 增加单元／API 测试：重叠组去重、不同 benchmark 不误合并、日期和 run 透传、无前一日、稳定排序与只读性。
5. `strategy_transition` 和 `group_phase_change` 明确返回 `deferred` 能力状态；本步骤不为缺失字段建立新的跨 run 索引或 report 解析框架。

完成标准：真实 run 能返回指标变化列表；重复的相同事实不重复计数；不同 benchmark 不误合并；接口不写数据库、不触发采集；后端相关测试通过。

暂停点：完成后开发 Agent 必须停下并报告 diff 与测试结果，由主 Agent review。不得自行开始数据库、首页或板块关系算法。

### 第 2 步：发现首页的最小可用界面

1. 新建 `DiscoveryView`，把 `/` 改为发现首页；保留 `/instruments/:symbol`。
2. AppShell 主导航加入“发现”，旧收藏链接继续有效。
3. 页面首屏显示证据日期、对比日期、覆盖／质量和 6–10 条变化；没有足够记录就少显示。
4. 卡片只显示对象、此前→当前、优先原因、支持／反对事实与两个入口：看个股、比较同类。
5. 提供“全部／个股／板块”和“只看重点关注外”筛选；暂不做复杂状态管理。

完成标准：1440×900 首屏能看见变化记录；加载、空、部分失败、无可比历史明确区分；键盘可达；路由测试和视图测试通过。

### 第 3 步：个人重点关注

1. 增加一张最小 focus symbol 表及迁移，使用现有 repository／session 方式。
2. 接入三个接口；PUT 幂等，symbol 使用现有规范化规则。
3. 首页和个股页提供加入／移出操作；首页能筛出“尚未重点关注”。
4. 明确验证 Universe 和 Observation Group 未发生变化。

完成标准：刷新与重启后关注状态保留；加入关注不会改变采集范围；接口和 UI 测试通过。

### 第 4 步：个股页重排

1. 删除重复的红色“当前无有效突破计划”展示路径，只保留一次可解释状态。
2. 将算法建议从窄侧栏移为图表前的全宽主区；当前约五个策略默认全部可见。
3. 每个策略显示方向、阶段、此前→当前、关键支持、未满足条件、确认和失效；实现 ID 放到次级信息。
4. 从发现页进入时突出对应事件和策略，并锁定发现的 run；直接搜索进入则显示最新可用证据。
5. “当前判断”、突破机会与策略建议的身份必须核对后合并；不能仅凭名称相似拼接。

完成标准：首屏能回答“为什么现在值得看、什么还不支持”；红色警告不重复；图表和期权区仍可用；个股测试通过。

### 第 5 步：指标／策略一览页变成紧凑比较表

1. 保留 `/indicators` 与 `/strategies` 独立入口，共用表格组件和查询状态。
2. 默认按 symbol+lens+证据上下文去重，组作为标签；可切换按组查看。
3. 把日期、搜索、组、重点关注、状态和排序压到顶部 160–200px 内；固定表头。
4. 明示排序字段和方向。指标页提供新变化、变化幅度、当前值、距条件；策略页提供阶段变化、新确认、接近确认、失效。
5. 中文名作为主标题，版本与实现 ID 放说明；退步、方向改变与改善使用不同文字，不能共用上箭头。
6. 从发现进入时定位并高亮相关行，返回恢复原筛选与位置。

完成标准：1440×900 首屏至少约 8 行；同一变化不因多组重复；空白和大段说明显著减少；现有横截面测试更新并通过。

### 第 6 步：板块启动阶段

1. 先复用已有 Group Decision Phase、Sample Support 和排名资格，生成“边际改善／参与扩散／广泛强势／开始恶化”的事实型阶段变化；不再建立第二套板块评分。
2. ETF、主题篮子、单股票组分开；单股票组不得升级为板块启动。
3. 展开时显示参与成员数、广度变化、相对强弱变化、集中度和不支持成员。
4. 第一版只使用当前与前一冻结快照。两点数据能证明方向和扩散，不能证明“已经持续多日”；此时必须显示持续时长未知，不能用“已走一段”措辞。
5. 用逐日历史回放检查单一龙头驱动、成员变化和缺失日期造成的假变化。只有连续同口径快照达到所需时长后，才开放“持续天数／已走一段／最近加速”。

完成标准：页面能区分少数龙头与更多成员共同改善；小样本和不可比较数据不会产生强结论；只有两个时点时不显示虚假的持续阶段。

### 第 7 步：有限的板块关系／跷跷板

只有第 6 步的组口径和回放可靠后开始。

1. 先由主 Agent 选少量有意义且口径可比的板块对，不做全组合扫描。
2. 在共同交易日、共同市场参考和固定成员口径下，计算 A/B 相对表现差的变化。
3. 分开“领先关系改变”和“持续反向强弱”；至少跨多个可比时点才允许命名持续关系。
4. 关系展开显示 A、B、市场参考、开始日期、持续长度、最近是否加速，以及支持／不支持成员。

实现门槛：第 6 步只有当前／前一两个时点时，第 7 步最多展示“本日领先关系变化”，不得命名“持续跷跷板”。需要先增加按 group version 与交易日读取连续冻结快照的窄查询，并验证成员、benchmark 与日期口径连续；不新增通用时间序列平台。

完成标准：同时上涨但领先改变、单日反向、持续反向、关系减弱四种情形能被区分；任何关系都能追溯到相同日期和样本。

### 第 8 步：整体验收和部署

主 Agent 负责：

1. review 每个阶段 diff，检查是否引入未授权抽象或把 UI 文案当事实计算；
2. 运行后端相关测试、前端单测、构建和真实浏览器关键路径；
3. 用至少两个真实 Observation Run 核对去重、日期、空状态和跳转；
4. 检查桌面和平板布局；
5. 确认旧容器无需保留后，再按现有部署流程替换运行版本。

部署前必须满足：没有重复红色警告；首页记录与详情证据一致；关注操作不改 Universe；指标／策略页排序可见；板块关系若尚未完成则清楚标为未提供，不能用涨跌幅榜或组内 rotation 冒充。

## 4. 开发 Agent 的工作规则

每次只接收一个阶段。开发 Agent 负责实现、必要测试和事实报告，不负责扩大范围、判断产品完成度、merge 或部署。

每个阶段交付时报告：修改文件、接口／页面行为、测试命令与结果、仍未覆盖的明确事项。遇到产品含义不清时保留事实字段并停下，不自行发明评分、阈值或“智能”结论。

以下行为视为偏离任务：创建通用事件框架；新增消息队列或缓存层而没有测得的性能问题；为个人系统建立账号／权限；重新实现已有 CrossSection 计算；同时重写全部页面；把后续阶段顺手带入当前 diff；将测试通过等同于产品完成。

## 5. 主 Agent 的 review 清单

- **事实边界**：所有变化都来自同一冻结 run 及可比前序；无前序时不伪造变化。
- **身份与去重**：重叠组只合并相同 lens 和证据；组标签完整保留。
- **可解释性**：每条记录能展示前值、当前值、日期和来源；排序原因可读。
- **页面闭环**：发现→详情／横截面→返回仍在同一证据上下文。
- **简洁性**：新模块数量与本阶段职责相称；没有为假设的未来需求增加基础设施。
- **回归**：旧路由、观察运行、个股图表、期权和配置页面保持可用。
- **完成度**：按阶段验收标准和真实浏览器结果判断，不接受只凭自动化测试的自评。
