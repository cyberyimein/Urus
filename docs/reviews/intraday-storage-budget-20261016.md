# 日内股票数据保留与容量预算（设计测算）

日期：2026-10-16。状态：同库归一化实现已进入收尾验收，尚未部署。下方早期类型化 SQLite 测算保留为设计记录，最新实际 JSON／revision／refs 模式的隔离测量见本段；均不代表生产新增数据实测。用户允许为指标适当延长历史，但须计算数据量。仅约束股票日内观察；不调整 Eoflora、期权或日线存储。

## 最新实现测量与口径

新设计在既有 collector.sqlite 中存储去重 bar revision 和唯一 quote batch，shard/finalizer 只存引用。旧日内 inline JSON 不原地转换，不清理 Eoflora 数据。

| 100 股，23 日 5m + 2 日 1m，仅 bars | 193,392,640 B（184.43 MiB） | 0（测量时） | 179,400 根 5m + 78,000 根 1m；TTL apply 前，不含 quote/ref/raw |
| 100 股，完整 2 日 156 槽 Runtime | 92,160,000 B（87.89 MiB） | 峰值 4,667,992 B（4.45 MiB），checkpoint 后 0 | 含 quote、3 shards／槽、finalizer、refs、ledger；尚无此前19日5m |

第二项含 156 quote batches／15,600 quote rows、468 shard raw、156 final raw、2,184 refs；股票逻辑合计 57,795,163 B（55.12 MiB），新股票表及索引 84,914,176 B（80.98 MiB）。完整 21 日指标加 2 日原始的统一 fixture 尚在补测，不能把上述两组相加称为实测稳态。

150／512 MiB 与 1 GiB 的运行门控使用股票逻辑字节；该值不包含全部 SQLite 页／索引，物理文件由 dbstat（可用时）和主库/WAL 单独观测。共享主库原有约9.5 GiB绝不能归入股票超限或清理范围。备份和独立 preview 也不计入活跃保留预算。

详见 [独立测试报告](intraday-predeploy-test-report-20261016.md)。以下早期 46.05 MiB 类型化 bars 数字不再作为当前实现的落盘承诺。

## 保留窗口

- 原始股票采集包、报价明细、事件：最近 2 个交易日，含当日。
- 指标输入：去重后的完整 5 分钟 OHLCV、成交额、来源／复权／质量／观察时间及 capture 身份，最近 21 个交易日，含当日，即此前 20 个交易日加当日。RVOL 只使用当日之前的同时间槽有效样本，至少 10 个，不把今天计入历史基线。
- 不长期保留重复分钟原始包，不重复存储每轮全部指标序列；优先用同一份去重 5 分钟线计算 MACD、ATR、MA、RS、RVOL。当天 session VWAP 仍需聚合真实成交额／量及覆盖证明，不能由收盘价近似。
- 21 日是上限而非假定已齐备；半日市、缺失、D 组轮换均不能填造样本，不足则指标不可用。优先日常积累，补采亦让位于 Eoflora，不为快速填满窗口无界回补。

## 行数与落盘测算

正常美股交易日 390 分钟，即 78 根 5 分钟线。按全部股票每个时段完整覆盖作上界：`N × 78 × 21` 行。半日市和缺失通常降低行数；多来源、复权口径及修订会增加行数，须另计且不无限保留 revision。

用标准库 sqlite3 在临时目录构造类型化 bars 表，字段为 symbol/provider/adjustment/timeframe/bar_end_at、OHLC、volume、turnover、quality_state、observed_at、capture_id，含复合主键和时间索引。每股价格、交易日及槽位不同；为体积测算使用连续日期标签，不作为日历或策略测试。无压缩、无生产数据、无 provider。以下只量 bars 主库；不含原始包、事件、WAL、备份及完整契约桥接所需的额外证据。

| 股票数 | 21 日 5 分钟行数 | 合成 SQLite 落盘 | 3 倍规划余量 |
| --- | ---: | ---: | ---: |
| 20 | 32,760 | 9.14 MiB | 27.43 MiB |
| 60 | 98,280 | 27.58 MiB | 82.73 MiB |
| 100 | 163,800 | 46.05 MiB | 138.14 MiB |

实测约 293–295 字节／行（含上述索引）。3 倍仅为规划余量，不是已验证的容量保证；最终实现须带实际字段、证据引用、索引和多日写入复测。

当前股票捕获把截至 cutoff 的当日分钟线重复放进 JSON。以当前分钟字段构造单行 JSON 样例 350 字节：完整 78 轮累计 `5 × (1+…+78) = 15,405` 行／股／日，而实际不同分钟只有 390 根，重复约 39.5 倍。

| 股票数 | 两天重复原始分钟 JSON 估算 |
| --- | ---: |
| 20 | 205.68 MiB |
| 60 | 617.04 MiB |
| 100 | 1,028.39 MiB |

此原始包估算不含 quotes、契约 envelope、quota audit、JSON 分隔、索引和重试，也没有计入压缩效果；价格数字长度不同会变化。D 组每 15 分钟采集会减少重复，但预算不能假定始终有 D 组。历史请求仍可能返回全日分钟，存储去重不等于减少 API 请求。

## 容量控制与下一切片

1. 先开发 Eoflora 优先让步，再扩展跨日采集。股票内部 A→B→C→D；后台历史预热最后执行。保留现有逐请求准入及共享 pacing，预留 Eoflora 待用代码和安全缓冲；不改变其配置。
2. 优先落地一份 21 日去重 5 分钟输入，不另建 RVOL 数据仓库。原始包若采用压缩，必须保持解码后的原始契约与 hash、P3/P7 回放一致，现有读取器适配后才能启用；不得直接篡改已冻结 capture 或用当前数据重建过去观察。
3. 初始按 100 股规划：指标数据预算 150 MiB；原始包预算 512 MiB；事件／消费进度／股票诊断预算 64 MiB；本功能活跃存储目标低于 1 GiB，余量覆盖 SQLite 临时增长与 WAL。均为待验证预算，独立导出／备份另计；共享文件须统计本功能逻辑字节并监控文件和 WAL 总大小，不把 Eoflora 数据归入本功能清理范围。
4. 时间窗口与容量双重控制。达到股票预算前先停历史预热和 D 组；仍无法保障安全写入时跳过新股票采集并记录容量原因，不无限堆积原始包，也不牺牲 Eoflora。先测压缩及日增长，再确定 512 MiB 是否能容纳实际两日，不能承诺压缩率或完整两日原始包必然保存。
5. 清理仅按明确股票归属生成 dry-run，核对消费者进度、事件／回放引用和外键。原始包过期后仅保留 hash 不代表仍能逐槽审计，网页与回放须明确超出证据保留期；5 分钟输入用于指标，不冒充长期原始事件回放。实际删除须取得具体操作指示，不对生产库执行 VACUUM／清理。
6. 验收覆盖 21 日交易窗口与此前 20 日排除当日、2 日原始包窗口、数据去重与修订有界、MACD／RVOL 结果一致、断点恢复、容量降级、Eoflora 不受影响及读取旧契约。测量主库／WAL／文件合计、每日新增和保留期稳态，不仅统计净 bar 行数。
